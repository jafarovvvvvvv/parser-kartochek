# parser_kartochek

Telegram-бот, который по названию товара ищет и сравнивает цены на
Wildberries, Kaspi.kz, Sulpak, Технодоме и DNS (Ozon исключён из поиска — см.
ниже), умеет отслеживать цену конкретного товара с уведомлением при
снижении и сам охотится за уценкой Sulpak (`/deals`, см. ниже). Город по
умолчанию — Костанай (`KASPI_CITY`/`TECHNODOM_CITY_ID`/`TECHNODOM_CITY_SLUG`/
`SULPAK_CITY_ID` в `config.py`), цены Kaspi/Технодома/Sulpak и сам состав
уценки зависят от города.

## Интерфейс: кнопки вместо команд

Бот рассчитан на телефон, поэтому всё, что раньше делалось набором команд,
теперь делается нажатием инлайн-кнопки:

- под карточками сравнения — кнопки 📌 N: поставить товар на отслеживание;
- в `/list` — кнопка ❌ у каждого товара: снять с отслеживания;
- под каждой находкой уценки — «📷 Фото дефектов (N)», «🔕 Скрыть модель»,
  «🔎 Сравнить в магазинах»;
- `/settings` — порог скидки кнопками ±5%, подписка, «проверить сейчас»,
  список скрытых моделей с возвратом по нажатию.

Команды остались для тех, кто привык, и регистрируются в меню Telegram
(`setMyCommands` при старте) — подсказываются прямо в поле ввода.

Как это устроено: `getUpdates` просит `allowed_updates=["message",
"callback_query"]` (без этого нажатия просто не приходят), нажатие приходит как
`update["callback_query"]` с полем `data` вида `действие:аргумент` (≤64 байт) и
разбирается в `bot.handle_callback`. На каждое нажатие обязательно отвечаем
`answerCallbackQuery` — иначе кнопка у пользователя «крутит часики» до таймаута.
Всё, что нужно кнопке после перезапуска бота, берётся из базы, а не из памяти:
у находки по номеру документа в `seen_deals` лежат магазин, код модели,
название, ссылка и фото. Исключение — `📌 N` после поиска: результаты поиска
живут в памяти, и после рестарта кнопка честно просит поискать заново.

Разметка сообщений — **HTML**, а не Markdown: в названиях товаров и описаниях
дефектов встречаются `* _ [ ]`, и как Markdown Telegram такое не принимает.
В HTML экранировать надо только `< > &` (`tg.escape`), и всё, что пришло из
магазинов или от ИИ, через него проходит.

## Охота за уценкой Sulpak (`deals.py`)

Отдельный воркер: раз в `KARTOCHEK_DEALS_SCAN_INTERVAL_MIN` (по умолчанию 3 ч)
обходит раздел уценки, отбирает экземпляры со скидкой выше порога и шлёт
находку подписчикам `/deals on`. **Порог свой у каждого магазина**
(`deals.min_discount(shop)`): у DNS распределение скидок в разделе уценки
структурно ниже, чем у Sulpak (максимум 59%, в основном 20-49% — проверено
вживую по Костанаю, у Sulpak регулярно 70-85%), и один общий порог означал бы
либо что DNS никогда ничего не проходит, либо что Sulpak заваливает находками.
Дефолт DNS — 40%, у остальных — `KARTOCHEK_DEALS_MIN_DISCOUNT` (70%). Порог
меняется кнопками ±5% в `/settings` или командой `/deals dns 40` /
`/deals sulpak 60`; голая `/deals 50` (без названия магазина) задаёт общее
значение по умолчанию — оно действует только для магазинов, у которых нет
своего override. Все настройки живут в `settings`. Находка помечается показанной
**только если реально доставлена** — иначе сбой отправки навсегда прячет
товар, о котором никто не узнал. В сообщении — цена уценённого, обе базы для сравнения, дефекты
конкретного экземпляра, адрес магазина и цена такого же **нового** товара в
других магазинах.

Как устроена уценка в Sulpak (найдено сниффингом живого сайта):

- Раздел — `/Discounted`, оттуда берутся id категорий; листинг категории —
  `GET /DiscountedProducts/{page}/{класс}/~/~/~/~/~/PopularityDesc/default`
  (страница за страницей, пока приходят новые карточки; по 15 на страницу).
  Карточки — те же `data-name/data-code/data-price`, что и в поиске, но здесь
  важна ещё зачёркнутая цена: она лежит не в data-атрибутах, а ниже по
  разметке (`product__item-price-old`), поэтому HTML режется по границам
  карточек, а не ищется рядом с совпадением.
- **Город задаётся кукой `city_id`** (6 — Костанай, 1 — Алматы), а не
  параметром запроса; `/Home/SetCity` для этого не нужен. Это не косметика:
  в разных городах уценка **разная** (в Алматы 17 категорий и сотня позиций,
  в Костанае 12 категорий и ~25) — проверено вживую сравнением двух городов.
- Сами уценённые экземпляры и их дефекты в листинге не показываются: они
  приходят из вкладки «Уценённый товар» —
  `POST /Goods/LoadCheaperPage` с полями `code`, `productTitle`,
  `mainImageUrl`, `fullPrice` (form-urlencoded). **Все четыре обязательны** —
  без `productTitle`/`mainImageUrl` эндпоинт отвечает 500. `fullPrice` берётся
  со страницы товара из `data-full-price` (это цена нового такого же).
- Одна модель = несколько физических экземпляров, у каждого свой документ
  уценки (`data-document`, например `ЦО2313010415`), своя цена, свой адрес
  магазина и свой набор дефектов. Поэтому единица учёта в коде —
  `models.DiscountedUnit` (экземпляр), а не товар, и дедуп алертов идёт по
  номеру документа: два одинаковых холодильника с разными дефектами — две
  разные находки, повторный обход того же экземпляра — не находка.
  **Но сообщение — одно на модель**, экземпляры идут в нём списком: в Костанае
  нашлось 6 уценённых AirPods одной модели в одном магазине, и отдельным
  сообщением на каждый бот превращался в спам (дублей при этом не было —
  экземпляры действительно разные, проверено по номерам документов). Сравнение
  с другими магазинами у экземпляров одной модели всё равно общее, поэтому и
  ищется один раз.
- **Фото самого экземпляра** (царапины, вмятины, а не стоковая картинка
  модели) лежат во фрагменте `LoadCheaperPage` — отдельный запрос не нужен.
  Хост другой, чем у фото модели: `https://discounted.object.pscloud.io/…jpg`,
  по ~3 на экземпляр, отдаются без кук. Каждая ссылка встречается в разметке
  дважды (href и фон) — дедуп внутри экземпляра. Проверено вживую: из 72
  экземпляров Костаная фото есть у 55, у разных экземпляров одной модели списки
  фото разные. В сообщение фото не встраиваются — это кнопка «📷 Фото дефектов»,
  по которой приходит альбом: иначе каждая находка превращалась бы в пачку
  картинок. Ссылки хранятся в `seen_deals.photos`, поэтому кнопка работает и
  после перезапуска.
- Рейтинг и число отзывов модели берутся со страницы товара, которая и так
  качается ради `data-full-price`. Матчится пара «значение + текст с числом
  отзывов»: ниже на странице форма «оставить отзыв» повторяет значение звёзд,
  но без текста — без этой пары подхватывался дефолт формы.
- Дефекты приходят готовыми парами «заголовок → текст»
  (`product__cheaper-more-item`): «Комментарий продавца» (например «Замена
  помпы», «Диагностика. Аппарат исправен»), «Упаковка», «Комплектация»
  (внутри — потёртости/царапины/вмятины по частям корпуса) и «Адрес».
- Скидку считаем от **двух** баз, потому что сам Sulpak считает её от третьей:
  на вкладке уценки показывается процент от текущей цены нового
  (`data-full-price`), а на карточке листинга зачёркнута другая, более высокая
  цена. Обе идут в сообщение (`discount_vs_new` и `discount_vs_old`), порог
  срабатывания — по большей из них (`best_discount`). Бывает и так, что
  `data-full-price` выше зачёркнутой цены — поэтому «максимум из двух», а не
  «одна правильная».

Поиск такого же нового товара в других магазинах (`find_cheapest_analog`) —
два независимых способа, результаты объединяются, берётся минимум по цене:

1. Строгое совпадение по артикулу модели в названии (`same_model`) — работает
   без ИИ. Хвост до 3 символов прощается (`MDR-EX15LP` ↔ `MDR-EX15LPV` — это
   цвет), дальше уже разные модели линейки (`HW60-BP12919` ≠ `HW60-BP12929`,
   `CSO4 276TWMB-07` ≠ `CSO44 286TWMB-07` — проверено на живой выдаче).
2. Та же батч-группировка ИИ, что и в обычном поиске: уценённый товар
   подкладывается в список кандидатов, берётся то, что ИИ положил с ним в одну
   группу. Нужна потому, что артикул есть не везде — Kaspi пишет просто
   «Наушники Huawei FreeBuds 5i чёрный».

Перед сравнением кандидаты просеиваются от **запчастей и аксессуаров**
(`looks_like_part`): они носят в названии артикул той же модели, и сравнение по
артикулу принимало их за тот же товар. Вживую это дало уценённой стиральной
машине за 124 995 ₸ «такой же новый» за 6 440 ₸ — подшипники к ней же — и вывод
«уценка не выгодна», то есть ровно ту дезинформацию, ради недопущения которой
сравнение и делается. Признаки: слово из списка запчастей в названии, оборот
«X **для** Y» (когда в нашем названии предлога нет — иначе отвалилось бы
«Средство **для** очистки кофемашины»), и предохранитель по цене — дешевле 20%
от цены нового это почти наверняка часть товара, а не он сам.

Если товар не опознан ни одним способом — в сообщении честно «сравнить не с
чем», а не похожий товар за неимением лучшего. Если новый в другом магазине
оказался дешевле уценённого — это прямо написано в сообщении («уценка не
выгодна»): молчать об этом нельзя, ради этого сравнение и делается.
В чужие магазины уходит **короткий** запрос (`short_query`, 5 слов без
повторов и скобок) — по полному названию из Sulpak магазины отдают пустоту,
это та же болезнь, из-за которой появился `query_planner`.

## Статус

- **Планирование запроса (`query_planner.py`)** — перед поиском ИИ превращает
  описание пользователя в короткий запрос для магазинов ("планшет с хорошим "
  "железом, экраном..." → запрос "планшет" + критерии "мощное железо, экран, "
  "динамики" для последующего ИИ-сравнения). Это критично: магазины (особенно
  Технодом/DNS) на длинные предложения с прилагательными возвращали 0
  результатов, на короткое слово — нормальную выдачу. Если категория товара
  вообще не ясна ("хочу подарок") — вместо поиска задаёт один уточняющий
  вопрос, следующее сообщение уходит туда же как ответ (до
  `MAX_CLARIFY_ROUNDS=2`, дальше ищет как есть, чтобы не зациклить диалог).
  Ранжирование (`relevance.py`) при этом всё равно работает по полному
  тексту пользователя, а не по короткому запросу — иначе теряются детали
  вроде цвета. Проверено вживую на обоих сценариях (прямой поиск и
  уточнение).
- **Wildberries** — работает, проверено вживую (поиск и обновление цены,
  прямой JSON API), но `search.wb.ru` умеет отвечать 403/429 при частых
  запросах — похоже на рейт-лимит/блокировку по IP, воспроизвёл вживую при
  интенсивном тестировании. `http_client.get_json` в этом случае делает
  пару повторов с паузой и только потом фолбэк на `curl`; если магазин так
  и не ответил, поиск теперь явно помечается как *"не отвечает"*, а не
  тихо показывается как "ничего не нашлось" (это было главной путаницей).
  Если это стабильно повторяется на боевом хостинге — велика вероятность,
  что WB блокирует конкретно его IP; смотреть лог `wb search ...: N сырых,
  M с ценой` и `adapter wildberries failed: ...` в `docker compose logs`.
- **Kaspi.kz** — работает, проверено вживую через Playwright (headless
  Chromium): страница поиска — SPA, парсим `.item-card` после рендера,
  цену/имя на карточке товара обновляем через `.item__price-once` /
  `.item__heading`. Капчи не встретили.
- **Ozon** — не работает и **исключён из `bot.py`/`scheduler.py`** (был в
  ADAPTERS раньше). Показывает интерактивную капчу ("Antibot Captcha") даже
  headless-браузеру с реалистичным профилем — подтверждено вживую, включая
  `/robots.txt`, что похоже на блокировку по IP дата-центра, а не только по
  фингерпринту браузера. Раньше при каждом поиске в ответе висела строка
  "не отвечает" без какой-либо пользы — чистый шум, поэтому убрали из
  активного пайплайна. Код (`adapters/ozon.py`) остался нетронутым: на
  реальном хостинге бота (другой IP) стоит перепроверить, снимется ли
  блок — если да, доработать селекторы карточек (не проверены на живой
  выдаче) и вернуть в `ADAPTERS`.
- **Sulpak** — работает, без браузера вообще: реальный поиск —
  `POST /Search/LoadProducts/1/77/~/~/~/~/~/PopularityDesc/tiles` (form-urlencoded,
  найден через сниффинг сети в Playwright, `?query=` через капитал `/Search`,
  не `/search`). Ответ — JSON с HTML-фрагментом внутри, карточки парсим по
  `data-name/data-code/data-price/data-brand` регуляркой (см. `adapters/sulpak.py`).
  `fetch_price` — обычный GET страницы товара, те же `data-*` атрибуты.
  Два бага, найденных и исправленных вживую: (1) кириллица в `Referer`
  роняла httpx (`UnicodeEncodeError`, заголовки должны быть ASCII) — не
  вылезало на латинице типа "iphone 15", всплыло на "Гарри Поттер"; (2)
  `data-price="1000000.0"` — собственный плейсхолдер Sulpak для товаров
  "Нет в наличии", не настоящая цена — теперь отфильтровывается.
- **Технодом** — работает, без браузера, и с лучшими характеристиками из
  всех магазинов: `POST https://api.technodom.kz/katalog/api/v2/products/search`
  (JSON), `client_id`/`session_id` — просто произвольные строки, не
  валидируются. `short_description` в ответе даёт готовую таблицу
  характеристик (экран, процессор, память, вес и т.д.). `fetch_price` —
  тот же эндпоинт с SKU как текстом запроса (поиск по SKU реально находит
  ровно этот товар).
- **DNS (dns-shop.kz)** — работает через Playwright: сайт за Cloudflare
  ("Just a moment..."), но в этой сессии проходит без вмешательства. Поиск
  — `.catalog-product` в DOM, но цена подгружается отдельным AJAX
  (`ajax-state/product-buy`) — нужно дождаться, пока в карточке появится "₸"
  (`page.wait_for_function`). Для `fetch_price` — проще и быстрее: цена уже
  есть в `<script type="application/ld+json">` (schema.org/Product) на
  странице товара, ждать AJAX не нужно. Два бага, найденных и исправленных
  вживую: (1) цена парсилась из `innerText` карточки регуляркой с `\s`, а он
  ловит и перевод строки — последняя характеристика склеивалась с ценой, и
  "IP54\n66 490 ₸" превращалось в 5 466 490 ₸ (в выдаче по airpods почти все
  цены были завышены в ~100 раз, и такая «цена» молча участвовала в
  сравнении); теперь в числе разрешены только пробелы, включая неразрывный.
  (2) `fetch_price` читал JSON-LD сразу после `domcontentloaded`, когда его в
  DOM ещё нет, и молча возвращал `None` — отслеживание цены DNS-товаров почти
  не работало; теперь ждём появления скрипта, берём блок именно с
  `@type: Product` (их на странице несколько) и делаем одну повторную попытку
  на случай, когда Cloudflare отдаёт страницу не с первого раза.
- Все адаптеры реализуют общий интерфейс `adapters/base.ShopAdapter`, так
  что добавление/починка магазина не потребует менять бота или БД.
- **Релевантность, нормализация и карточки моделей** — после поиска бот
  тянет с каждой площадки топ-15, `relevance.py` локально отсекает
  откровенно нерелевантное по совпадению слов с запросом (без ИИ, топ-4 на
  магазин остаётся кандидатами). Дальше **один** батч-вызов OpenAI
  (`grouping.py`, модель из `OPENAI_MODEL`) над всем плоским списком
  кандидатов разом: (1) отбрасывает то, что не относится к категории товара
  из `query_planner.py` (например наушники/пылесос/чехол в выдаче по "планшет
  Xiaomi" — раньше долетало до пользователя), и (2) схлопывает одинаковые
  модели из разных магазинов в одну группу (`models.ProductGroup`). Ось
  группировки — бренд + модель + объём памяти + диагональ + LTE/Wi-Fi;
  **цвет в неё не входит** — это атрибут конкретного предложения
  (`models.Product.variant`), а не отдельная модель, иначе один и тот же
  Xiaomi Pad 7 в трёх расцветках занимал все карточки, а другие модели
  вообще не попадали в ответ (поймано на реальном запросе — исправлено).
  Цвет виден в строке предложения ("Kaspi.kz (синий) — ..."), а если
  пользователь сам назвал цвет в критериях — ИИ фильтрует предложения по
  нему внутри карточки, не плодит группы. Внутри группы — точно один и тот
  же товар (без учёта цвета), поэтому "дешевле всего" в `compare.py`
  считается кодом (`min` по цене) с указанием цвета победившего предложения,
  а не выдумывается ИИ — раньше при сравнении вперемешку разных товаров ИИ
  иногда называл "самым дешёвым" не то, с чем реально сравнивал
  пользователь, это подрывало доверие к боту. Тот же риск с другой стороны:
  ИИ иногда раскладывает одну модель на две группы (Sony MDR-ZX310AP «с
  микрофоном» и «просто проводные»), и тогда «дешевле всего» считается внутри
  половины — в выдаче стояла пометка на 18 670 при 5 990 в соседней карточке.
  Поэтому после ИИ группы с одинаковым названием модели схлопываются кодом
  (`_merge_same_model`). `compare.py`
  рендерит не больше `MAX_GROUPS=3` карточек (модель → характеристики →
  цены по магазинам, дешевле — с пометкой), одним сообщением. Вторым
  (необязательным) сообщением — короткая рекомендация от ИИ (`advice.py`),
  какую из показанных моделей взять с учётом критериев пользователя
  (характеристики, не цена — цену уже видно в карточке, ИИ её не
  пересчитывает, только ссылается). Если модель одна и критериев нет —
  сообщение не шлётся, советовать нечего. **Важно:**
  `gpt-5.6-luna` — reasoning-модель; без `"reasoning_effort": "none"` она
  тратит весь `max_completion_tokens` на скрытые размышления и отдаёт
  пустой ответ — поймано вживую в `query_planner.py`/`grouping.py`,
  исправлено. Без `OPENAI_API_KEY` в `.env` группировка деградирует до
  склейки по буквально совпадающему названию (`grouping._fallback`), без
  фильтрации мусора — остальной бот работает как раньше.
- **Голосовой ввод** — можно прислать голосовое вместо текста, бот
  расшифрует (`voice.py`, OpenAI `gpt-transcribe`, OGG→mp3 через ffmpeg),
  покажет распознанный текст и обработает его как обычное сообщение.
  Проверено вживую на реальном аудио (ffmpeg-конвертация + распознавание +
  дальнейший поиск). Паттерн общий для всех ботов в этой инфраструктуре —
  см. memory `voice-input-pattern`.

## Структура

- `models.py` — модели `Product`, `ProductGroup` (одна модель товара из
  нескольких магазинов)
- `adapters/`
  - `wildberries.py` — прямой JSON API (search.wb.ru / card.wb.ru)
  - `sulpak.py` — прямой API (Search/LoadProducts), HTML-фрагмент внутри JSON
  - `technodom.py` — прямой JSON API (api.technodom.kz), лучшие характеристики
  - `kaspi.py` — Playwright, парсинг DOM
  - `dns.py` — Playwright (Cloudflare), DOM + JSON-LD для fetch_price
  - `ozon.py` — Playwright, упирается в капчу (см. выше)
  - `playwright_client.py` — общий stealth-браузер (маскировка
    navigator.webdriver, блокировка картинок/шрифтов, общий Chromium-процесс).
    Запуск браузера под `asyncio.Lock`: поиск и обход уценки могли одновременно
    увидеть «браузера нет» и поднять два Chromium, один из которых осиротевал и
    держал память в контейнере, живущем неделями (проверено: 8 одновременных
    страниц — ровно один запуск). Контексты переиспользуются из небольшого пула
    (до 4), с очисткой кук перед выдачей — единое общее состояние на всех дало
    бы гонку кук города Kaspi между параллельными вызовами.
  - `base.py` — интерфейс `ShopAdapter`
- `http_client.py` — HTTP-слой для прямых API: GET/POST (json/form/raw),
  ретраи, ротация User-Agent, детект блокировки, фолбэк на `curl` для
  эндпоинтов, режущих httpx по TLS-отпечатку (обнаружено на `card.wb.ru`)
- `compare.py` — рендер карточек `ProductGroup` в текст для Telegram
- `grouping.py` — батч-фильтрация по категории + группировка одинаковых
  моделей в `ProductGroup` одним вызовом ИИ (см. выше)
- `advice.py` — короткая финальная рекомендация ИИ поверх уже готовых
  карточек (см. выше), вторым сообщением
- `query_planner.py` — превращает запрос пользователя в короткий поисковый
  запрос + category + критерии, либо просит уточнить (см. выше)
- `deals.py` — охота за уценкой Sulpak: обход раздела по расписанию, порог
  скидки, сравнение с новым товаром в других магазинах, алерт в Telegram
- `db.py` — sqlite (без ORM): отслеживаемые товары + история цен +
  показанные находки уценки (`seen_deals`) и подписчики на них
- `tg.py` — голый транспорт Telegram Bot API (long polling, скачивание файлов).
  Отказы Telegram поднимаются как `TelegramError` с текстом из поля
  `description`, а не через `raise_for_status()`: раньше на любой 400 (а
  «сломана разметка» — это именно 400) летел `httpx.HTTPStatusError`, который
  `send_message` не ловил, и фолбэк на текст без Markdown не срабатывал
  никогда — сообщение просто терялось. Заодно httpx кладёт в текст ошибки URL,
  а в нём токен бота, и он утекал в логи. `parse_mode=None` — отправить
  заведомо без разметки (так шлются находки уценки: в описании дефектов
  попадаются `*`, `_`, `[`). **Параметры со значением `None` не отправляются
  вовсе**: на `{"parse_mode": null}` Telegram отвечает `400 unsupported
  parse_mode`, из-за чего первый живой `/deals scan` не доставил ни одной
  находки. Мок-тест этого не поймал — проверять отправку надо реальным
  вызовом API, пусть и одним сообщением.
- `voice.py` — расшифровка голосовых через OpenAI (gpt-transcribe)
- `bot.py` — команды `/track`, `/list`, `/untrack`, `/deals on|off|scan`,
  поиск по тексту/голосу.
  Офсет Telegram-апдейта сохраняется ДО обработки сообщения, а не после —
  иначе рестарт контейнера (например, от `/deploy`) во время долгой
  обработки (поиск + ИИ, 20-90 сек) приводил к повторной обработке того же
  апдейта и дублированию ответа пользователю (поймано вживую, исправлено).
- `scheduler.py` — периодическая проверка цен и алерт при снижении. Запросы
  группируются по (магазин, id товара): если один товар отслеживают из
  нескольких чатов, в магазин идёт один запрос, уведомления — всем.
- `main.py` — точка входа: три воркера (опрос Telegram, проверка цен, охота за
  уценкой), каждый под своим «надзирателем» `_supervise`. Раньше это был голый
  `asyncio.gather`, и необработанное исключение в одном воркере отменяло
  остальные — падал весь бот. Теперь упавший воркер логируется и
  перезапускается через 30 секунд (без паузы постоянная причина сбоя крутила бы
  перезапуск в тугом цикле), остальные продолжают работать.
- `adapters/registry.py` — единый список магазинов. Раньше он собирался
  отдельно в `bot.py`, `scheduler.py` и `deals.py`, причём с разным составом
  (Ozon висел только в `scheduler.py`).
- `ai.py` — общий слой вызовов OpenAI (`ask_json`, `ask_text`) для
  `query_planner.py`, `grouping.py` и `advice.py`: раньше один и тот же код
  повторялся трижды, включая обязательный `"reasoning_effort": "none"`.
  Любой сбой (нет ключа, сеть, пустой ответ) возвращает `None`/пустую строку, а
  не исключение — у всех трёх вызывающих есть запасной вариант.

## Запуск

```
cp .env.example .env   # вписать KARTOCHEK_BOT_TOKEN
docker compose up -d --build
```

Dockerfile на базе `mcr.microsoft.com/playwright/python:v1.60.0-noble` — в
нём уже есть все системные библиотеки для Chromium, отдельно ничего ставить
не нужно.

## Тесты

```
pip install -r requirements-dev.txt
python -m pytest tests -q
```

Без сети и без браузера, около 6 секунд. Тесты написаны не «для покрытия», а
против конкретных поломок, которые уже случались на живых данных, — поэтому по
названию упавшего теста сразу видно, какая регрессия вернулась: склейка цены
DNS с характеристикой («5 466 490 ₸»), запчасть вместо товара в сравнении,
совпадение артикулов одинаковой длины «самих с собой», `null` в параметрах
Telegram, потеря находки при сбое отправки, пометка «дешевле всего» внутри
половины группы, падение истории цен после повторного `/track`. Отдельно —
поток находок целиком (лимит за обход, очередь, скрытые модели, падение одного
магазина, одновременные обходы) и интерфейс на кнопках. Сеть подменяется на
уровне httpx, а не функций транспорта: так работает настоящий `tg.call()` со
своей фильтрацией `None`.
